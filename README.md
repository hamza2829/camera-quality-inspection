# camera-quality-inspection

[![CPU inspection checks](https://github.com/hamza2829/camera-quality-inspection/actions/workflows/ci.yml/badge.svg)](https://github.com/hamza2829/camera-quality-inspection/actions/workflows/ci.yml)

## What it is

A small Python example of a machine-to-cloud **shaped** inspection pipeline:
synthetic camera frames → OpenCV and a small PyTorch CNN → JSON/MQTT adapter →
validated SQLite records. **All images are generated by this code. There is no real
machine data, real camera, or deployed cloud service.**

The images are 96×96 grayscale metal-like textures with illumination variation,
noise, and a scratch, dent, hole, or no defect. Both methods decide pass/fail;
OpenCV also reports contour positions, bounding boxes, and areas in pixels. The
CNN is a binary image classifier, not a detector or defect-type classifier.

## How it works

1. **Generate:** fixed seed `20261101`; independently seeded train/validation/test
   streams with 600/180/180 images. Every split is 50% clean, with 1/6 each scratch,
   dent, and hole. Each defective image contains one simulated defect. `labels.csv`
   records image ID, split, defect type, pixel position/size, contrast, and noise.
   IDs hash image pixels. Separate RNG streams prevent train-size changes from
   changing test images. This is not a measured model of real metal optics.
2. **Inspect:** OpenCV median denoising, Gaussian background removal, residual
   thresholding, morphological close/open, and contour extraction. A qualifying
   region means fail. Twelve threshold/min-area combinations are compared on
   validation F1. Thin scratches and shallow dents can be erased by preprocessing.
3. **Learn:** a small CNN trains from scratch for ten CPU epochs using denoised
   intensity and residual channels. Lowest validation BCE selects the checkpoint;
   validation F1 selects a threshold from 0.10–0.90. Test labels never select
   parameters. Precision, recall, F1, and confusion matrices use the same held-out
   test images for both methods. Positive means defective/fail.
   CI checks execution and records measurements; it does not enforce an accuracy target.
4. **Publish:** the camera simulator serializes metadata plus both methods' actual
   results. A conservative final rule fails an image if either method fails.
   JSON excludes ground-truth defect labels. Timestamps use a fixed simulated
   clock, not actual acquisition times. Images/model weights are not sent over MQTT.
5. **Consume:** a strict Pydantic contract checks version, synthetic source, types,
   finite probabilities, decision consistency, timestamps, and pixel bounds. SQLite
   has a primary key on image ID. Exact message replay is a no-op; different content
   for an existing ID is rejected, preserving the first record. Each load commits
   in a transaction. The mock benchmark publishes the test set twice to exercise replay.

The optional paho-mqtt adapter uses callback API v2 and QoS 1, waits for publish
acknowledgement, and stores before consumer acknowledgement. Invalid/conflicting
messages are logged and discarded; a database error disconnects without ack so an
operator can reconnect/replay. The local mock bypasses MQTT networking entirely.
See [the pipeline contract](docs/pipeline.md) for scope and failure behavior.

## What is NOT done

- **Synthetic data only:** no industrial dataset, production metal, real camera,
  camera calibration, acquisition timing, or physical defect measurements.
- **No GPU:** training and inference use CPU. No pretrained model or YOLO weights.
- **No live MQTT broker in CI:** publisher/consumer interactions are mocked. No
  claim of testing MQTT protocol behavior, broker persistence, reconnect handling,
  authentication/TLS, throughput, or network delivery guarantees.
- No actual cloud deployment, object storage upload, factory PLC connection,
  real-time control, or automated reject actuator.
- No detection AP/IoU benchmark, CNN localization, multi-defect benchmark,
  multi-seed uncertainty study, drift monitoring, or production accuracy claim.
- No durable producer outbox or automated recovery/retry orchestration. QoS 1 and
  SQLite idempotency do not make this an end-to-end exactly-once system.
- **No Docker is needed** for development, tests, training, or the optional native broker.

## How to run locally

Use Python **3.11** and a fresh virtual environment. Commands from the repo root:

```sh
python -m venv .venv
# Linux/macOS:
. .venv/bin/activate
# PowerShell instead: .venv\Scripts\Activate.ps1
python -m pip install torch==2.7.1 --index-url https://download.pytorch.org/whl/cpu
python -m pip install -e ".[dev]"
python -m pytest -q
python -m camera_quality.experiment --output artifacts/local --epochs 10
```

The experiment generates images and `labels.csv`, trains the CNN, evaluates both
methods, renders three marked examples, and runs the mock pipeline/replay. Outputs
include `metrics.json`, `evaluation.md`, `predictions.json`, `training.json`,
`model.pt`, and `inspection.sqlite`. Use a **fresh output directory** on each run
(for example `artifacts/second-run`) to preserve earlier measurements. The dataset,
checkpoint, and SQLite outputs are ignored by Git; the checked-in report/examples
are a selected CI snapshot. Seeded CPU runs can still differ across platforms or
library versions; the checked-in report identifies its actual CI source.

Replay without a broker, after generating predictions:

```sh
python -m camera_quality.pipeline mock --predictions artifacts/local/predictions.json --database artifacts/replay.sqlite
```

Optional live local transport: install/start a **native Mosquitto** broker separately
on localhost, then run these in two terminals using the same environment:

```sh
python -m camera_quality.pipeline consume --database artifacts/live.sqlite
python -m camera_quality.pipeline publish --predictions artifacts/local/predictions.json
```

The optional adapter defaults to localhost port 1883 with no TLS or credentials.
It is a local demonstration, has not been exercised against a live broker here,
and must not be exposed as a production service. No broker is needed for tests or
the default experiment. CI runs tests and the same ten-epoch experiment on every
push/PR and retains generated artifacts for 30 days.
